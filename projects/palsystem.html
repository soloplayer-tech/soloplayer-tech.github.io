CASE 01

슬롯 인벤토리의 요청과 확정 분리

문제·요구사항
드래그앤드롭 화면이 보유 아이템의 기준이 되면 서버 상태와 불일치할 수 있습니다.
구현과 판단
클라이언트는 Server RPC로 요청하고 실제 Items 배열 변경은 Authority 경로에서 처리합니다. 슬롯 범위·수량·최대 스택을 확인하고 OnRep_Items에서 화면 갱신 이벤트를 전달합니다.
  1. 슬롯 입력
  2. Server RPC
  3. Authority 배열 변경
  4. OnRep → UI

구현 범위와 확인 항목

  • 동일 아이템 스택 병합과 빈 슬롯 탐색
  • 슬롯 간 이동·교환과 수량 처리
  • 월드 드랍 생성 실패 시 아이템 복구 경로
핵심 코드 펼쳐 보기 ＋
void UPWPlayerInventoryLinkComponent::OnRep_Items()
{
    OnInventoryChanged.Broadcast();
}
인벤토리 구현 ↗인벤토리·UI 담당 커밋 ↗

CASE 02

인벤토리·장비·표현의 연결

문제·요구사항
아이템을 장착할 때 슬롯 타입과 보유 수량을 확인하고, 변경된 장비를 다른 클라이언트 화면에도 반영해야 합니다.
구현과 판단
서버 장착 경로에서 슬롯 유효성과 타입 호환성을 검사합니다. 복제된 EquipmentSlots와 선택 슬롯을 기준으로 장착 메시와 현재 도구 상태를 갱신합니다. 장비 해제는 인벤토리 반환의 성공 여부를 먼저 확인합니다.

구현 범위와 확인 항목

  • 인벤토리 ↔ 장비 슬롯 이동과 타입 검사
  • 선택 퀵 슬롯과 주 행동 연결
  • RepNotify에서 장착 시각 상태와 UI 갱신
핵심 코드 펼쳐 보기 ＋
void UPWPlayerEquipmentComponent::OnRep_EquipmentSlots()
{
    EnsureSlotCount();
    RebuildVisualComponents();
    SyncSelectedToolToPrimaryActionComponent();
    OnEquipmentChanged.Broadcast();
}
장비 구현 ↗담당 소스 폴더 ↗본인 커밋 이력 ↗

CASE 03

기능별 플레이어 컴포넌트 구성

문제·요구사항
이동·등반·상호작용·장비·UI가 플레이어 클래스 한곳에 모이면 기능 변경의 영향 범위가 커집니다.
구현과 판단
Action·Climb·Stat·Equipment·InventoryLink·PrimaryAction 컴포넌트로 역할을 나누고 캐릭터를 중심으로 연결했습니다. 후속 작업에서는 스피어 투척과 소환 관련 경로도 확장했습니다.

구현 범위와 확인 항목

  • 구르기·등반과 스태미나 처리
  • 아이템 정의와 장착 도구별 주 행동 연결
  • 후속 구현과 확인되지 않은 완성 범위를 구분
플레이어 구조 ↗등반 컴포넌트 ↗후속 작업 커밋 ↗

현재 범위와 다음 확인

주요 소개 범위는 플레이어·인벤토리·장비·UI입니다. 스피어 투척·포획·소환 관련 코드도 존재하지만 전체 완성이나 패키징 멀티플레이 검증을 의미하지 않습니다. RPC 요청의 게임 규칙 검증과 복제 비용 개선은 추가 과제입니다.
